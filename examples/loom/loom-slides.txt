SLIDE 1 - Loom hardware architecture

A per-host switch in FPGA logic. Routes memory transactions, not packets.

- One interface: loads / stores / DMA to peer-mapped pointers
- Same pointer reaches local or remote memory - the caller never picks

Blocks (all vFPGA user logic, no shell changes)

- Aperture - 15 x 4 KB windows; the app's plain loads and stores land here,
  and the address itself names the destination (bits 15:12 = window,
  bits 11:0 = offset)
- Control Registers - the CSR page, programmed by loomd; also where bulk DMA
  descriptors are staged and triggered
- Window Table - 15 entries: valid, route, pid, VA base, len; one lookup per
  transaction
- Order FIFO - everything enters in arrival order; the ordering guarantee, so
  a flag can never overtake the bulk it follows
- TX Engine - one transaction at a time: store, DMA, fence, read
- RX Engine - lands incoming traffic: message parse, bulk forward

Sits between the Coyote Host I/O Stack (AXI-Lite, host DMA, TLB) and the
Coyote Network I/O Stack (RC queue pair, RoCEv2).

Two routes, one interface

- Local  -> cross-pid host write: the shell TLB translates into another
   process's address space
- Remote -> RDMA write over RC. Bulk goes direct (RETH = exporter's VA);
   a sub-64 B store rides a 64 B inline message

Wire format: offset-op-len. No tokens, no tags, no sequence numbers.

Per host: 1 vFPGA, 1 control daemon (loomd), daemon-to-daemon TCP for setup

SLIDE 2 - Status

WORKS (on silicon)

- Local route: complete. 19/19 functional, 10/10 aperture, bulk sweep clean
  from 64 B to 16 MB
- Remote route: correct up to 16 KB, verified byte-for-byte by the receiving
  host (sender-side completion proves nothing)
- Wire format, inline messages, direct bulk, cross-pid landing, cross-host
  ordering - all confirmed
- Costs: lookup 2 cyc, store 2 cyc, fence 2 cyc, local DMA ~424 cyc at 4 KB

FAILS - remote sweep breaks at 64 KB and above

- 64 B to 16 KB, 0.03-5.94 GB/s: intact
- 64 KB, 10.08 GB/s: CORRUPT
- 256 KB, 11.9 GB/s: CORRUPT
- 1 MB and 4 MB: never reached, the run stops

- Corruption is not subtle: payload lands displaced by whole packets,
  ~7700 of 8192 words wrong
- Receiver drops -> one drop cascades (go-back-N) -> 1000s of retransmissions

BUT IT IS NOT A SIZE LIMIT - IT IS RATE

Same 64 KB transfer, only concurrency changed:

- 1 descriptor in flight, 2.02 GB/s: intact
- 4 descriptors in flight, 8.80 GB/s: intact
- 32 descriptors in flight, 9.87 GB/s: corrupt

- Identical size, identical request shape on both sides of the cliff
- So: a throughput limit, not a protocol or format bug
- Ceiling bracketed: 8.80 clean / 9.87 corrupt
- Big sizes fail in the sweep because they are the ones issued fast enough
  to cross it

ROOT CAUSE + NEXT STEP

- Fixed per-packet cost: ~450 ns budget against 64 cycles of actual data
  - spends as long again per packet as the payload itself
- Prime suspect: RX is single-outstanding, pays request latency serially
- Diagnostic bitstream in build now - partitions every receive cycle
  (moving / starved / stalled) and splits stalls before vs after the first
  beat, which picks between the two candidate fixes

NOT TESTED YET - LOCAL + REMOTE TOGETHER

- Single-host tests program only local windows; the two-host test programs
  only remote windows. Never mixed in one run.
- So these are unverified on hardware:
  - cross-route ordering: a local store ordered against a remote bulk,
    which is the point of having one order FIFO
  - both routes interleaved back-to-back through the same engine
  - local and remote windows live in the same table at the same time
- Nothing suggests it is broken - it has simply never been exercised

NOT BUILT YET

- Remote loads (RDMA READ) - currently returns poison by contract
- TX coalescer (needed for the full throughput curve)
- Per-role deployment binaries

ONE-LINER

Correct, not yet fast. Remote transfers are byte-exact up to 16 KB; above
~9 GB/s the receive path runs out and fails by corrupting rather than
pushing back.
